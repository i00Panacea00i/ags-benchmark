## 一、测试目标

1. 以**系统最高并发**（maker 并发 12 实例 + 预热池 6）执行完整工作单元链路：
   候选发现 → 沙箱内制作（配对/克隆/F2P 验证/LLM 改写）→ 每题镜像构建推送 TCR → 入库；
2. 全程记录准备、执行、结果三阶段，采集吞吐、延迟、漏斗、故障数据；
3. 基于实测数据分析架构性能表现，定位瓶颈，提出优化设计。

### 2.2 方法

- **并发压测参数**：`--concurrency 12 --warm 6`（池信号量背压 + 预热实例即取即用）；
- **三个测量阶段**：① CVM 侧单元发现（GitHub 搜索式配对 + 结构双筛）；
  ② 沙箱内制作（完整 F2P 双向 ×2 轮 + 稳定性筛选 + DeepSeek 改写 + 镜像构建推送）；
  ③ 验证（tccli 临时工具生命周期，**未及执行即终止**）；
- **数据采集**：驱动池指标（实例创建延迟/acquire 等待）、漏斗逐级统计、claim 状态、
  数据集 digest 校验、产物 mtime 取证、TCR 远端核对。

## 五、瓶颈分析

1. **仓库环境兼容性是最大漏斗杀手（43.6%）**：attrs / marshmallow 全军覆没于
   `ImportError`（env-lock 仅含运行时依赖，缺测试依赖），aiohttp 全灭于 C 扩展构建失败。
   题目候选质量本身没有问题——是**环境配方生成环节**的系统性缺陷；
2. **发现产出率 16.7% 且优质池易枯竭**：半数候选死于维护者不写 closing keywords
   （pallets 系仓库文化），rich 深池 0/43 通过；本轮 4 轮补充发现耗时 ~25 分钟，
   占总时长近半；
3. **验证吞吐受工具配额硬约束（本次未实测，架构推算）**：每题临时工具上限
   并发 8（配额 10 − 固定 1 − 余量），单题验证周期 ≈4-5 分钟 → ≈90 题/小时天花板；
   相比制作端 ≈400 题/小时的能力，**验证是下一阶段的真正瓶颈**；
4. **驱动生命周期健壮性**：会话绑定（D2）与孤儿实例回收（D3）在故障注入下暴露缺口。

## 六、优化建议（按优先级）

| # | 建议 | 预期收益 | 成本 |
|---|---|---|---|
| O1 | **env-lock 增强**：纳入 pyproject dev/test 依赖组；发现阶段加 60 秒沙箱探针（`pip install + pytest --collect-only` 预检） | 挽回 ~40% 漏斗损失（17→~4），成功率 43.6%→~80% | 低（脚本级） |
| O2 | **仓库兼容性矩阵 + 配方缓存**：按仓库沉淀环境配方（repo → env recipe），新题复用 | 新仓库一次性成本，老仓库零损失 | 中 |
| O3 | **验证侧提配额/降周期**：向平台申请工具配额提升（10→30）或复用同 digest 工具；验证预热并行化 | 验证吞吐 90→300+ 题/小时 | 商务/中 |
| O4 | 驱动 `setsid` 脱离会话 + 崩溃 finalizer（孤儿实例强杀 + claim 回写，对齐 validator_driver 已有清扫机制） | 消除 D2/D3 类残留 | 低 |
| O5 | 发现阶段常驻候选池服务 + GraphQL 批量查询（4 调用→1），多 Token 轮换 | 发现耗时 25 分钟→<5 分钟 | 中 |
| O6 | 补丁体量上限 500→700 行（本轮 2 个合法单元被误杀） | +2 单元/池 | 极低 |

## 七、结论

- **制作链路性能优异**：12 并发下 25 单元 114 秒、单单元 90 秒、池 acquire 零等待，
  相比 v1 架构提速 7 倍，吞吐推算 ≈400 题/小时，远超验证端容量；
- **压测达成工程价值**：热修复 1 个并发缺陷（D1），暴露 3 类系统性瓶颈（环境配方、
  发现产出、驱动生命周期），全部有明确优化路径（O1–O6）；
- **数据资产**：17 个可验证的 benchmark 镜像（F2P 68 / P2P 278）已入库，
  验证管线就绪（工具配额 1/10 清洁）；
- **建议下一步**：先落地 O1/O4（低成本高收益）→ 申请 O3 配额 → 复跑
  「制作+验证」全链压测并纳入 Phase B（LLM 解题率）测量。
